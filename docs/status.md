# Implementation status

What is built, measured against `docs/spec.md`. Updated with each slice.

## On the branch k3s: moving from Docker Swarm to Kubernetes

The platform runs on k3s (v1.37.2, pods under crun): every system stack is a `kubernetes.yaml` that the deployer applies with `kubectl` in the namespace `garrison`; Traefik routes Ingress objects; Secrets, ConfigMaps from the stacks' files, ZFS datasets as hostPath volumes; NetworkPolicies take the place of Swarm's networks (`garrison/platform`); metrics come from the kubelet and the Kubernetes API, logs from Alloy reading pods. The agents' sandboxes are pods under gVisor in `garrison-sandboxes`, held to an admission policy. The VM steps base, install, login and agent are green on it. The apps run on it too, each environment in a namespace of its own (`app-<stack>`), with their datasets as hostPath volumes, snapshots before redeploys, and Secrets kept when an app is removed. More machines are still to move; the rest of what follows describes main, on Swarm. How Garrison uses Kubernetes: [kubernetes.md](kubernetes.md).

## Works, tested end to end on a fresh Ubuntu 26.04 VM

`test/vm/steps.sh` runs the end-to-end test as a tree on Multipass VMs: fixtures (base, install, login, agent, deploy, team), saved as snapshots, and scenarios, each in a throwaway clone of its fixture, up to four at once; see `test/README.md`.

- `install.sh --answers FILE`: installs Docker and ZFS, initialises Swarm, creates the ZFS pool, generates secrets, deploys the bootstrap stacks in order (Postgres, Traefik, Keycloak, login proxy, Gitea, Actions runner), waits for Gitea Actions to build the control plane, and hands over to its deployer. Safe to run again.
- Units are Gitea organisations. The system stack is the organisation `garrison`, one repo per stack: `postgres`, `traefik`, `keycloak`, `sso`, `gitea`, `runner`, `control-plane`, `grafana`, `prometheus`, `loki`, and `platform` for contracts. Everyone signed in can read them; only root admins can change them. Gitea shows nothing without signing in.
- Deployer: runs in Swarm and deploys every repo of `garrison` that holds a `compose.yaml`, itself last, as soon as Gitea's webhook reports a change (and every 15 s otherwise); a deleted repo's stack is taken down. Its image is built from `garrison/control-plane` by Gitea Actions on the `garrison` organisation's runner, pushed to Gitea's registry, and deployed by a commit that sets the tag in that repo's `compose.yaml`.
- Single sign-on: people sign in to the Keycloak realm `garrison`. Private environments redirect to that login and pass the signed-in person's identity to the app. Gitea and Grafana sign in through Keycloak.
- Roles: the Keycloak group `root-admins` holds the people who may change the platform. Its members are Gitea admins and Grafana admins; everyone else views. Both re-read the groups at every login. `garrison/keycloak/add-user.sh` adds people.
- Monitoring: Grafana (`grafana.<domain>`) with Prometheus (node, container and Traefik metrics) and Loki (container logs), neither reachable from outside. Dashboards are code: any repo's `dashboards/*.json` goes into a Grafana folder per unit, kept as on `main` by the deployer; `garrison/grafana` brings Overview, Stack, Logs, Machine, Traffic and Agents. Agents' sandboxes are measured but their output, the conversations, is kept out of Loki.
- Alerts: the deployer tells Prometheus how each Swarm service does (desired, running and recently failed tasks, labelled with unit, app and environment, which it stamps on every app service; the platform's own count as `garrison`). Prometheus's rules (`garrison/prometheus/alerts.yml`, tested with promtool by `alerts_test.yml`): ServiceFailing (3 failed tasks in 10 minutes), ServiceDown (fewer tasks running than wanted for 5 minutes), HighErrorRate (over a fifth of an app's requests answered 5xx for 5 minutes), DiskAlmostFull (under 10% free), TargetDown. Alertmanager sends each, with a token, to the agent service, which puts it in the dashboard's feed for the unit's people (and its resolution, on the same entry) and starts the unit's routines that wait for it (`on_alert` in `agent.yaml`), once per firing.
- Chat: Open WebUI at `chat.<domain>`, signed in through Keycloak. Every unit has a permanent channel, its team chat, which only its people read (`garrison`'s everyone reads), and the agents answer there when mentioned by name, `@operator`, working in the channel's unit. The agents are Garrison's: folders in `garrison/config` (`agents/<name>/agent.yaml`, `prompt.md`, skills), which root admins change, the operator and the commander to begin with; units have none of their own, and give the agents rights and routines there in `grants.yaml` and `routines.yaml` of their config; Open WebUI talks to them through the agent service in the control plane, which runs each chat with an agent in a sandbox of its own: a container with Pi, the agent harness, and a workspace kept in a volume per chat, which gets the LLM (only the agent service has the key) and the agent's tools at the gateway through the agent service, and can clone the repos the person may read and propose its changes as a pull request by them; the gateway keeps the agents and channels in sync with Gitea and serves each agent only its own tools, acting with each person's own Keycloak token: they read stacks, logs, metrics and repos, and propose changes as pull requests a person merges in Gitea. Agents are for everyone; working in a unit where they have a grant or a routine on a private repo, they are for that unit's people only, and answer only in private chats and the unit's channel. A unit can give an agent grants: an account of its own in Gitea there, writing only to the repos granted, that proposes for people who may not write there and merges into the branches granted, for the groups each grant names; a change to a unit's repo goes with that unit's grants wherever it was asked. Sandboxes run under gVisor, as root, so agents install what a task needs, and reach the internet only through the agent service's proxy, as far as their `agent.yaml` says (`internet`: the package registries, named domains, or all; never the home network; the registries at most for agents on private repos). Agents ask each other for work (`ask_agent`), working where the asker does; chains of command (`chains/` in `garrison/config`) write down the order agents do a job in, run by their lead, known to every agent in them and to the commander, and runnable as a routine (`chain:`), e.g. `software-updates`: the sentry, the scout on the web, the coder's pull requests; the commander, the default in new chats and named in every channel's pinned message, finds the agent for what someone wants (`find_agents`) and hands the work over or says whom to ask. Agents run routines on a cron schedule, every so often or when a branch moves (kept in Postgres across restarts), with nobody watching, and use the apps' pages as the person (`browse`). The gateway brings open proposals up to date when their base moves. The LLM is Ollama's `gpt-oss:120b` by default. Models: several providers in `garrison/config` (`llm/providers.yaml`), and the list of their models (`llm/models.yaml`) kept current by a daily sync that proposes changes as pull requests: new models come turned off, retired ones are marked and their agents fall back to the default; agents name `<provider>/<model>`, checked on approval, and list them with `list_models`. A unit's media library is its share `media`: its agents see it at `/data/media`, and `stacks/files.yaml` (image `garrison/files`, Filebrowser behind Garrison's gate) shows it, its people changing files and everyone signed in looking. With `COMFYUI_URL` in `install.env`, `@media` makes pictures and videos with ComfyUI in a project's styles into it (`generate_media`) and cuts vertical shorts from them with ffmpeg. Root admins add a provider on the dashboard's Models page, with its URL and API key, or ask the operator (`add_provider`), which proposes it and links the page for the key. New config repos start from `templates/`. A new unit is set up within seconds (config, channel, build account), also one made by hand in Gitea; `create_unit` answers once it is ready. App repos' `main` is free in a unit of one person, and takes only pull requests another person approved once there are two or more. A merge deletes its pull request's branch by default, in every repo (set by the members sync, also for repos made by hand, as Gitea has no default for the installation), except in a repo an app deploys from a branch besides main, such as `dev`: there Gitea's box starts unticked, so merging dev into main keeps dev. The dashboard's and the agents' merges delete the branch unless it is an environment's; deleting `dev` by hand still takes its environment down. Routines ask their person with `ask_person`: a mention in the unit's channel and a "Waiting for you" list on the dashboard, which refreshes on its own, plays a short tone and counts in the tab's title when something new waits, and also lists the changes waiting for the person, each with a card in plain words and Approve and Merge buttons, the link agents give when they propose; the owner's reply in the thread resumes the run in its sandbox, for up to 24 hours.
- Apps: in every unit other than `garrison`, each file `config/stacks/<name>.yaml` is an app. With a `source` repo, it is deployed from that repo's branches (`main` → `<name>.<domain>`, `dev` → `dev-<name>.<domain>`) once its pipeline has built the commit's image, and with a `preview` environment each open pull request gets one, `pr-<n>-<name>.<domain>`, until it closes; without one, as the file says. App repos hold only code. The one example app is the template `todo` (`templates/app/todo`), which `create_repo` writes into a new repo: a Go and Postgres todo app, a list of their own for everyone signed in, with its tests, Dockerfile and pipeline, and in its README the stack to propose. The tests deploy it as `todo/app`, by `todo/config/stacks/todo.yaml`.
- Snapshots and restore: Sanoid snapshots all data, the platform's and the apps', hourly, daily and monthly (24, 30, 6 kept). Before redeploying an environment that holds data, the deployer snapshots its datasets (`deploy-<time>-<commit>`, 10 kept) and does not deploy if it cannot. To bring an environment's data back, a person (or an agent, which finds the snapshots with `list_snapshots`) proposes `restores/<name>.yaml` in the unit's config, naming the stack, environment and snapshot; the approval check validates it. Once merged, the deployer snapshots the current state (`restore-<time>`, so a restore can be undone), stops the environment's services, copies each of its datasets back from the snapshot and deploys it again. Each request runs once. Shares are not restored.
- Unit members: `<unit>/config/members.yaml`, applied to Gitea teams; changes only by approved pull request, and nobody approves their own role change. The agents can show members and propose changes but never approve or merge (`docs/scenarios.md`).
- Pipelines: a system runner for `garrison` and a user runner for every other unit, whose jobs reach Docker only through the control plane's guard and build images with BuildKit; one build account per unit for its registry.
- Reboot: `garrison-repair.service` replaces Swarm tasks that Docker restarted without their secrets or configs.
- Dashboard: at `https://<domain>/`, behind the sign-in, served by the control plane's `home` service. For now it is one page, the feed: everything that happens and how it was handled, newest first, updating itself every 5 seconds. Gitea's webhooks give pushes, branches, repos, pull requests, reviews, the approval check's verdicts and finished pipeline runs; the deployer adds each deploy, wait for an image, removal, restore and failure (each failure once, however often it recurs); the gateway adds every change an agent makes for someone (`propose_*`, `merge_change`, `screenshot`, `create_*`) and every refusal; the agent service adds each routine's run with its answer. Filters: unit, Everything / Code and reviews / Pipelines and deploys / Agents / Problems, and a search. An entry's page shows its thread, "how it was handled": the events of its pull request and its commits, and of a routine's run, followed one step further (a routine's proposal → its pull request → the merge → the pipeline and deploy of the merge commit). Each person sees the events of the repos Gitea lets them read; agents' calls and routine runs only the unit's people and the person they were for; root admins everything. The events are kept 90 days, in Postgres (`garrison`). `GET /api/events` and `/api/events/{id}` answer the same as JSON.
- Secrets: a unit's admins and root admins set, replace and delete its secrets on the dashboard's Secrets page (`https://<domain>/secrets`), which shows names, never values. The dashboard encrypts each value with SOPS for the unit's age key and the installation's recovery key, using their public halves alone, and commits `secrets/<name>.yaml` (and `.sops.yaml`) to config's `main` as the platform's account, the only one that may push there, with the person as author; the feed records it, for the unit's people. The deployer holds the units' keys (`/etc/garrison/sops`, made on first use, mounted only into it), gives the dashboard the public keys, and decrypts a stored secret only for the `main` environment of the stacks that name it, as a Swarm secret per version, redeploying it when one changes and removing earlier versions; other environments get generated values. The installer makes the recovery key and prints its private half once.
- CLI on the host (`garrison`): validates a stack file, claims its hostnames, creates its ZFS datasets and Swarm secrets, and deploys it behind Traefik; `applied` shows what the deployer deployed.

## Differs from the spec for now

| Spec | Now |
| --- | --- |
| Setup wizard in a bootstrap container | Answers file only; no wizard |
| Let's Encrypt wildcard via DNS challenge; Pebble in tests | Self-signed wildcard certificate generated by the installer |
| ZFS pool on a drive | A sparse file on the root disk, unless `POOL_DEVICE` is set |
| Hostname claims come from Git | Kept in `/var/lib/garrison/claims.json` |
| Restore from the History tab, code and data together, with a change record | A restore request, `restores/<name>.yaml` in the unit's config, brings back an environment's data only |
| Tests with and without a second virtual disk | One disk; Multipass cannot attach a second |
| — | Test installs pull Docker Hub images through `mirror.gcr.io` (`REGISTRY_MIRROR`) |

## Not started

History repos; change records and approvals in the deployer; of secrets: the agents' use of them (tokens, logins, an Ethereum signer, see the spec), the keys sealed to a TPM, rotation (`garrison secrets rotate`), and the platform's own (LLM key, DNS token) in `garrison`; the backup drive and restic; the dashboard beyond the feed (unit, stack and service pages, config forms), alerts to people's phones (ntfy).

## Known limits

Problems the platform cannot close itself, as Gitea, Open WebUI or Docker offer no way to, are in [unfixable.md](unfixable.md); ideas for later in [ideas.md](ideas.md).

- The apps, `dev-` environments and previews of private repos can be opened by everyone signed in, not only the unit's people (an idea to fix it is in [ideas.md](ideas.md)).

- The deployer pulls its image from the local Docker daemon, which built it. A second node would need registry credentials.
- The system runner's jobs can use the Docker daemon, which is root on the machine. It serves only the `garrison` organisation, which only root admins can write to.
- Agent sandboxes share one network with the agent service, so they can reach each other; nothing listens in them, but an agent could start a server. Their volumes are not yet removed when a chat is unused for long.
- An agent with internet can be talked into sending out what it reads. Agents on private repos reach only the registries, and an agent reaching more clones only public repos; but its platform tools still read what the person may read, private files included, and npm and crates.io accept uploads from anyone with an account of theirs, so even the registries are not a closed door. Give wide internet to agents for people you trust with the unit's data.
- What a sandbox installs goes to its container's layer on the root disk, without a size limit, until the container stops.
- In a channel, one sandbox serves all threads with an agent: Open WebUI names the channel, not the thread.
- Posts of routines and background answers come from the gateway's Open WebUI account, with the agent's name in bold, into the channel rather than a thread.
- A background `ask_agent` acts with the person's Keycloak token, which lasts five minutes.
- Previews' datasets and secrets stay after a preview is taken down.
- A stored secret reaches the code on its app's `main` branch, so whoever may push or merge there can read it through that code; the unit's members push to its app repos.
- The units' keys are files readable by root on the machine, not yet sealed to a TPM. An install made before secrets existed lacks `/etc/garrison/sops` and the recovery key: the deployer cannot start until `install.sh` runs again. Likewise one made before the model list lacks `/etc/garrison/llm-keys`, which the agent service needs.
- Provider keys set on the dashboard's Models page are secrets of `garrison`, `secrets/llm-<provider>.yaml`, which the deployer writes to `/etc/garrison/llm-keys`; the install's LLM key is still the file `/etc/garrison/llm-api-key`. Existing agents keep the tool lists their `agent.yaml` names; only new units get `tools: all`. Turning a model off in `models.yaml` takes effect within a minute; agents in a running sandbox switch at their next LLM request.
- The feed misses what happens while Postgres is down or before it answers (each service logs what it could not record), and Gitea events whose webhook delivery failed. An event's visibility is checked against the repo's rights now, not when it happened: once a repo is made private or deleted, its old events are hidden from those who can no longer read it.
- Snapshots stay on the pool's own disk: no backup drive or off-site copy yet. A restore copies files back rather than rolling back, which takes as long as the data is large, and needs the pool's free space for the data changed since. Change records and a restore of code and data together, as the spec's History describes, are not built: a restore brings back data only, and the app keeps running its current version.
- BuildKit runs privileged, outside Swarm. Build steps run in its own sandboxes without privileges; a flaw in BuildKit itself would reach the host. Its build cache is shared between units.
